# B121 费用预留审查与可执行选项（待确认）

## 范围与证据

属于现有 graphrefly:B121 的设计审查证据，由 graphrefly root 管理；不是费用回执、执行授权或新决策。用户“继续”授权本次调查与离线计算。执行代码、冻结输入、旧账及样本状态均未修改。

- `scripts/b121-comparison/api-transport.mjs` 的 create 在每次尝试前按整窗口输入＋本次输出上限预留；未知失败保留预留，同请求重试另行预留。
- `scripts/b121-comparison/api-provider.mjs` 的 estimateInput 明示 bytes/3+256 是启发式，不是上界。不能用它代替整窗口费用预留来宣称严格守住总额。
- 当前输入context为1,048,576，最大输出4,096。依冻结费率，最大预留$0.319488。
- [完整旧账](summary.json)已有$3.94176466保守占用；[逐笔证据](reservations.json)仍保留8笔未知费用。

## 外部限额能否替代未知预留

[OpenRouter官方说明](https://openrouter.zendesk.com/hc/en-us/articles/51690568268059-How-do-I-cap-my-spending-and-stop-runaway-usage-from-coding-agents)指出，key限制在请求前检查，实际费用请求后确定；大请求或并发可能超过限额。
[官方limits文档](https://openrouter.ai/docs/api/reference/limits)说明上游有在途预算和短暂结算窗口，但未为我们这8笔请求提供结算收据。

因此，key余额快照不是所有旧请求最终费用的证明。客户端串行也不能证明已超时的上游请求全部结束。这里没有得到可量化的延迟计费上限，不能把“key上限＋一笔请求”包装成严格总费用证明。

## 选择

| 方案 | 是否守住现有$4定义 | 能否立即解决 | 判断 |
|---|---|---|---|
| 等待逐笔结算证据 | 是 | 6笔无ID，当前不能 | 保留取证路径，不无限轮询 |
| 用token启发式压低预留 | 无法证明 | 看似可以 | 不采用 |
| 把旧未知移出准入，仅信key余额 | 改变原风险定义 | 看似可以 | 不采用；不能称旧费用已结算 |
| 保留旧账，累计预算改为$4.50 | 改变数额，不改变费用定义 | 可支持有限新运行 | 推荐提交用户确认 |

## 推荐的精确边界

累计上限从$4改为$4.50，仍包括全部历史已报告费用、全部未知预留、未来每次尝试的预留。旧未知释放$0；外部key上限$1.97、不重置、不充值、不换key。

保守可增加占用$0.55823534。预留下一笔最大请求后，成功调用可逐步结算使用的空间为$0.23874734；这不是承诺整轮一定能完成。一笔新的最大未知失败之后，下一次同额重试就不满足准入，应原样停止。

下一次若被批准，必须作为独立的新开发运行，保留固定四题分母，沿用当前模型/provider/任务/评分与资源参数；不恢复v7或仅补它的失败题，不承诺成功。需要新的单次执行manifest和冻结验证，旧执行授权不能重放。未触发正式holdout或library泛化结论。

## 离线验证

[7个边界算例](budget-option-calculation.json)以十进制精确计算全部通过：旧上限拒绝、新上限准入、一次未知失败后拒绝重试、$0.2成功成本后准入、$0.25后拒绝、精确边界准入、超出十亿分之一美元即拒绝。

这些是设计算例，不是已接入transport的测试；没有修改transport或伪称实现完成。若批准金额调整，后续需将新的费用常量与所有实际准入校验一致更新、测试并重新冻结，再执行一次。

## 审阅顺序

1. 旧账：8笔未知继续保留，避免用限额变更掩盖未结算。
2. 风险：$4.50仍按最坏费用占用计量，key限额仅为第二道控制。
3. 验证：明确一次新未知失败就可能终止新运行，避免预算变更被理解为必然通过。

批准前不修改执行上限，不发生成请求。这是当前明确$4数值边界的调整请求，不是要求重复授权已有离线工作。
