重复行按同一文件摘要和行号计数，仅包含 read 返回的源码行；不包含 task.json、search 匹配行或跨请求重发的对话历史。缓存占比来自 provider 回执，不表示同一源码被主动反复读取，也不意味着不消耗累计预算。以上均非独立 tokenizer 测量。

单次上下文并未接近本轮冻结的 1,048,576 上限。三题触发的是累计输入下的提交预留策略。不能据此继续提高上下文窗口或将四题通过称为自然、轻松完成。

源码行计数不能衡量每一行是否有用；没有对照，不能把成本单独归给文档、模型或 harness。分页80行与保留完整历史可能影响累计成本，但本轮没有测量其因果效应。自动删历史、Codex代总结或直接提供目标源码会改变实验条件，不能混入本轮成绩。

## 下一步顺序（准备方案，尚非正式冻结）

1. **停止针对这四道题继续调优。** 保留它们作为开发回归和运行链资格检查；连接缓解保留有限结论。下一轮不以旧题再次4/4为目标。

3. **先明确评分能证明什么。** 沿用已批准的编译与静态语义范围；若要声明运行时行为正确，先另行设计隔离执行及行为判据。不得因为新增运行时目标而追改本轮通过率。
4. **冻结后一次执行。** 固定模型/provider、library材料、工具、完整历史政策、80行分页、预算和提交预留策略；逐样本报告自然提交/预留提交、失败/未运行、最大单次输入和累计输入。保留失败，不补采到成功。
5. **有独立证据后再改 library。** 将真实问题归到 TS 包文档或实现；新旧版本在同一套新任务与同一 harness 条件下比较。仅有本轮4/4，不足以选择新的公开API或宣传易用性提升。
